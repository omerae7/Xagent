## ۲. موتور عمومی (بخش ۱۰ تا ۱۷)

- **انواع مأموریت:** یک‌باره، زمان‌بندی‌شده، تکرارشونده، رویدادمحور، شرطی، چندمرحله‌ای و تفویضی؛ تسک‌ها سه نوع دارند: `human` (فقط یادآوری)، `agent` (اجرای خودکار در موعد) و `dependent` (پس از پیش‌نیاز). سیاست زمان ازدست‌رفته: `run_late` یا `skip` (مهلت ۱ ساعت).
- **انتخاب روش اجرا (بخش ۱۲):** API ← داده ساختاریافته ← DOM ← بینایی؛ نبود API یعنی ناتوانی نیست: خطای گذرای ۵xx/Timeout/429 روی `http_request` خودکار به مرورگر می‌رود (گام «روش جایگزین» در تایم‌لاین).
- **مسیریاب مدل (بخش ۱۳):** سیاست‌های اقتصادی/متعادل/کیفیت/«دقیقاً زنجیره من» (پیش‌فرض، رفتار قبلی حفظ شد). معیار: هزینه مورد انتظار یک اجرای موفق = هزینه هر فراخوانی × تعداد ÷ احتمال موفقیت (قابلیت اطمینان بیزی از دفتر مصرف ۷ روز). قیمت حدس زده نمی‌شود؛ مدل بدون قیمت با قیمت محافظه‌کارانه Stop-Loss سنجیده می‌شود؛ سقف بودجه فیلتر سخت است.
- **راستی‌آزمایی و بازیابی (بخش ۱۴):** Checkpoint پس از هر ابزار؛ لغو اجرای والد به فرزندان می‌رسد؛ بازیابی پس از Crash بدون تکرار اقدام بیرونی (`test_J`).
- **چندکارمندی (بخش ۱۵):** گزارش مدیر از شواهد خروجی کارمندان و تخصیص هزینه به هر کارمند (`test_I`).
- **آداپتورهای عمومی (بخش ۱۶):** منبع `inbox` عمومی برای رویدادهای هر سرویس؛ هیچ روتین پیش‌فرض تلگرام ساخته نمی‌شود.
- **مشاهده‌پذیری (بخش ۱۹):** `GET /api/usage/breakdown?dimension=model|provider|employee|routine|mission|purpose|day|tool` و `GET /api/runs/{id}/metrics`؛ هزینه «برآوردی» همیشه جدا از «تأییدشده».

## ۹. محدودیت‌های شناخته‌شده

- کنترل مختصاتی دسکتاپ اثر عنصر را تشخیص نمی‌دهد (کنترل با دسته `desktop_control`).
- نشست مرورگر پس از ری‌استارت Worker از نو باز می‌شود؛ مدل باید دوباره صفحه را باز کند.
- هزینه Cursor از API مستند قابل استخراج نیست؛ سقف روزانه و هم‌زمانی تنها کنترل هزینه است.
- برای Kimi، `supports_reasoning`/`supports_image_in` فقط اگر API برگرداند ثبت می‌شود؛ کنترل thinking را کارفرما طبق مستندات هر مدل تنظیم می‌کند.
- Kimi Code ممکن است استفاده خارج از ابزارهای کدنویسی مجاز را محدود کند؛ هیچ User-Agent جعلی ارسال نمی‌شود.
- قطعی دیتابیس در میانه اجرای مدل و Timeout ابزارهای طولانی آزمون جداگانه ندارند.

## ۱۰. برنامه آزمون Staging (فقط با اجازه کارفرما)

1. نصب روی سرور آزمایشی جدا با پشتیبان و همین SHA؛ `xagent doctor`.
2. xAI و Kimi: کلید آزمایشی کم‌اعتبار ← «همگام‌سازی مدل‌ها» ← مقایسه قیمت‌ها با صفحه قیمت رسمی ← «تست اتصال» و «آزمون قابلیت‌ها».
3. Cursor: کلید + یک مخزن آزمایشی خصوصی ← «آزمون اتصال (بدون ساخت Agent)» ← یک کار کوچک با کارت اجازه ← پایش تا پایان ← بررسی شاخه/PR ← آزمون لغو.
4. تلگرام با حساب آزمایشی (نه حساب اصلی): مأموریت ده‌دقیقه‌ای با دو گفتگوی مجاز/غیرمجاز.
5. مرورگر واقعی: صفحه آزمایشی دارای دکمه‌های View/Edit/Delete/Pay.

## ۱۱. استقرار امن (پس از تأیید کارفرما)

```
sudo xagent update --ref <SHA نهایی> --dry-run   # بررسی تغییرات و Migrationهای 0006 و 0007
sudo xagent update --ref <SHA نهایی>             # پشتیبان خودکار، مهاجرت، Health Gate و Rollback خودکار در خرابی
```
پیش‌فرض‌ها امن‌اند: سیاست مسیریاب «دقیقاً زنجیره من»، Cursor غیرفعال، همه تسک‌های قدیمی `human`.

## ۱۲. ریسک‌های بازگشت (Rollback)

- بازگشت کد بدون Downgrade دیتابیس امن است (ستون‌ها/جدول تازه برای کد قدیمی ناشناخته و بی‌اثرند)، جز وضعیت `failed` تسک که کد قدیم آن را نمی‌شناسد (فقط نمایش).
- Downgrade به 0005 داده‌های بخش ۵ را حذف می‌کند؛ پیش از آن از پشتیبان خودکار استفاده کنید.
- Agentهای Cursor در حال اجرا با Rollback متوقف نمی‌شوند؛ پیش از بازگشت از پنل لغو کنید.
